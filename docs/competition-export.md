# การตั้งค่าไฟล์ส่งออกและตรวจรับกับทีมงาน

งาน Dashboard [#93](https://github.com/mojisejr/jaothui-dashboard/issues/93) และ source [#123](https://github.com/mojisejr/jaothui-event/issues/123)

ระบบใช้รูปแบบไฟล์ที่บันทึกแยกแต่ละงาน จึงรองรับลำดับรุ่นที่ต่างกันโดยไม่แก้โค้ด งานเก่าที่ไม่เคยตั้งค่า งานที่เพิ่งคัดลอก และงานที่มีค่ารุ่นหรือคำแปลขาด ต้องตรวจและบันทึกให้ครบก่อนดาวน์โหลด ไม่มีไฟล์บางส่วนหรือการเดารุ่นจากอายุให้โดยอัตโนมัติ

การทดสอบอัตโนมัติและการอ่านไฟล์กลับด้วยไลบรารีเป็นหลักฐานด้านโค้ดเท่านั้น **การใช้งานหน้าจอจริงและการคลิกลิงก์ใน Microsoft Excel ยังรอคุณนนท์ตรวจหลัง merge และขึ้น production ตามที่มอบหมาย** คู่มือนี้ไม่ได้บันทึกว่าผ่านการตรวจรับจริงแล้ว และไม่ได้อนุญาตให้ merge, deploy หรือแก้ข้อมูล production โดยอัตโนมัติ

## ตั้งค่างานเก่าหรืองานใหม่ครั้งแรก

1. เปิด `/dashboard/competitions` เลือกงานและแท็บส่งออก ตรวจชื่องานและรหัสงานให้ตรง ไม่อาศัยชื่องานอย่างเดียว เพราะชื่ออาจซ้ำกัน
2. ใน “รูปแบบไฟล์ของงานนี้” ตรวจร่างที่ระบบเสนอ ร่างเริ่มจากชุดรุ่นที่มีอยู่และค่าที่พบในใบสมัคร ไม่ได้อ่านป้ายหรือรู้ลำดับที่ผู้จัดต้องการ จัดลำดับหมวดด้วยปุ่มขึ้น/ลง แล้วระบุเลขรุ่นตามป้าย ชื่อเต็มภาษาไทย และชื่อย่อภาษาไทย
3. ผูกหมวดกับรุ่นต้นทางและค่ารุ่นเดิมให้ชัดเจน หากเป็นรุ่นที่หายจากชุดรุ่นปัจจุบัน ให้ระบุเป็นรุ่นประวัติเดิมและใช้ค่าต้นทางที่พบจริง ห้ามนำคนละรุ่นมารวมกันเพียงเพราะชื่อเหมือนกัน
4. ตรวจระดับประเทศหรือจังหวัด/ท้องถิ่น แล้วกำหนดกลุ่มสีและเพศตามลำดับที่ต้องใช้ ค่าเริ่มต้นเสนอผู้ก่อนเมีย แต่แต่ละงานปรับลำดับเองได้ รุ่นที่ประกวดรวมสียังคงแยกชีตตามสีและเพศ เลขรุ่นบนป้ายเดียวกันจึงมีหลายชีตได้
5. ใช้ชื่อย่อบอกเฉพาะรุ่น เช่น “ลูก” แล้วดูชื่อแท็บจริงในตัวอย่าง เช่น `ป01-ลูก-ดำ-ผู้` ชื่อแท็บมีระดับ เลขป้าย สี และเพศประกอบอยู่แล้ว ชื่อเต็มและเงื่อนไขที่ทีมงานต้องใช้ควรอยู่ในชื่อเต็มภาษาไทย ระบบจำกัดชื่อแท็บและแก้ชื่อชนกันโดยคงข้อมูลครบในสารบัญ
6. ตรวจ “ค่าต้นทางที่พบในใบสมัคร” และ “คำแปลและค่าต้นทางเดิม” ให้ครบ ค่าที่รู้จัก เช่น `male`/`female` และ `black`/`albino` แสดงเป็น ผู้/เมีย และ ดำ/เผือก ค่าที่ไม่รู้จักต้องมีการยืนยันความหมายและคำไทยก่อน ไม่เปลี่ยนค่าที่รู้จักให้มีความหมายผิด
7. กด “ดูตัวอย่างลำดับชีต” ตรวจลำดับ ชื่อแท็บ ชื่อเต็ม ระดับ สี เพศ และจำนวนใบสมัคร รวมทุกกลุ่มแล้วต้องตรงยอดรวม แก้คำเตือนให้ครบ แล้วกด “บันทึกรูปแบบไฟล์”
8. โหลดหน้าซ้ำ ยืนยันว่ารูปแบบที่บันทึกและตัวอย่างยังตรงกัน จึงดาวน์โหลด Excel หรือ ZIP ใบสมัคร DOCX หากมีร่างที่แก้ค้างไว้ ต้องดูตัวอย่างและบันทึก หรือเลือก “ใช้รูปแบบที่บันทึกแทนร่าง” ก่อนดาวน์โหลด

ชื่อเต็ม ชื่อย่อ และคำแปลที่ระบบสร้างต้องเป็นไทย ส่วนชื่อควาย ชื่อเจ้าของ ชื่อฟาร์ม ชื่องาน รหัส และข้อความส่วนบุคคลคงเดิม ไม่แปลทั้งไฟล์ด้วยการแทนคำทั่วไป ค่าต้นทางในฐานข้อมูลไม่ถูกเปลี่ยนจากการตั้งค่าการแสดงผล

## ตัวอย่างตรวจลำดับป้ายอุดรธานี

ตารางนี้เป็นตัวอย่างสำหรับตรวจการตั้งค่ากับป้ายที่ได้รับ ไม่ใช่ค่า hardcode ของระบบ และไม่แก้กติกาการสมัครหรือช่วงอายุเดิม ให้เทียบชุดรุ่นจริงของงานก่อนบันทึก โดยเฉพาะความต่างของขอบอายุรุ่นท้องถิ่นที่ควรแยกเป็นงานทบทวนกติกา หากพบไม่ตรงป้าย

| เลขป้ายประเทศ | หมวดที่ควรอยู่ต่อกันในตัวอย่าง                                                        |
| ------------- | ------------------------------------------------------------------------------------- |
| 01–04         | ควายดำ: ลูกควาย → ควายรุ่น → หนุ่ม–สาว → โตเต็มวัย                                    |
| 05–08         | ควายเผือก: ลูกควาย → ควายรุ่น → หนุ่ม–สาว → โตเต็มวัย                                 |
| 09            | ควายแคระ ฟันน้ำนม รวมสี                                                               |
| 10            | ควายแคระ ฟันแท้ตั้งแต่ 1 คู่ รวมสี                                                    |
| 11            | ควายใหญ่ ฟันน้ำนม รวมสี; เมียสูงตั้งแต่ 150 ซม. ผู้ตั้งแต่ 160 ซม. ตามป้าย            |
| 12            | ควายใหญ่ ฟันแท้ตั้งแต่ 1 คู่ รวมสี; เมียสูงตั้งแต่ 155 ซม. ผู้ตั้งแต่ 170 ซม. ตามป้าย |
| 13            | ควายยอดเยี่ยม รวมสี                                                                   |

หลังหมวดประเทศ ตรวจระดับจังหวัด/ท้องถิ่นแยกต่างหาก: เลข 01 ลูกควาย และเลข 02 ควายรุ่น รวมสีตามป้าย อย่าให้เลขของสองระดับทำให้ข้อมูลรวมกัน หากหมวดไม่มีใบสมัคร จะไม่มีชีตว่างและเลขป้ายหมวดถัดไปไม่เลื่อนตามจำนวนชีต

ต้องตรวจอีกหนึ่งงานที่ตั้งลำดับต่างออกไป เช่น หมวดท้องถิ่นก่อนประเทศหรือเผือกก่อนดำ เพื่อยืนยันว่าระบบใช้การตั้งค่าของแต่ละงาน ไม่ได้ใช้ลำดับตัวอย่างอุดรกับทุกงาน

## เมื่อมีค่าขาด ข้อมูลใหม่ หรือแก้พร้อมกัน

- หากแจ้งว่ามีใบสมัครที่ยังไม่ได้ผูกกลุ่มหรือยังไม่มีคำไทย ให้แก้รายการที่ระบุก่อนดาวน์โหลด ไม่ตัดทิ้ง ไม่รวมเข้ารุ่นอื่นตามชื่อย่อ และไม่ใช้ “ไม่ระบุ” ซ่อนค่าที่มีข้อมูลแต่ผิดรูปแบบ
- กรณีข้อมูลว่างจริง สามารถตั้งค่าคำเทียบค่าว่างเป็น “ไม่ระบุ” อย่างชัดเจนได้ ต้องคงความแตกต่างจากค่าที่รู้จัก เช่น ค่าว่างไม่เท่ากับผู้ ดำ หรือระดับประเทศ
- ใบสมัครใหม่หลังดูตัวอย่างอาจมีสี เพศ ระดับ หรือรุ่นเดิมที่ยังไม่เคยตั้งค่า ระบบตรวจใหม่ตอนดาวน์โหลดเสมอ จึงอาจหยุดให้แก้แม้ตัวอย่างก่อนหน้าพร้อม
- หากชุดรุ่นเปลี่ยน ให้กด “โหลดข้อมูลล่าสุดโดยเก็บร่าง” ตรวจการผูกหมวดกับชุดรุ่นล่าสุด แล้วใช้ “ยืนยันตรวจชุดรุ่นล่าสุดแล้ว” เมื่อได้ตรวจจริง ดูตัวอย่างใหม่และบันทึก ไม่กดข้ามเพื่อให้ดาวน์โหลดได้เฉย ๆ
- หากบันทึกชนกับการแก้จากอีกหน้าหรืออีกคน ร่างต้องยังอยู่ โหลดข้อมูลล่าสุดและเทียบก่อนบันทึกอีกครั้ง ไม่บังคับทับข้อมูลเก่า การคัดลอกงานต้องตรวจร่างของงานปลายทางใหม่ ไม่ถือว่ารูปแบบต้นทางผ่านการตรวจของงานใหม่แล้ว
- หากแจ้งว่าข้อมูลต้นทางกำลังอัปเดตหรือยอดใบสมัครไม่ตรง ให้โหลดใหม่ หากยังไม่ตรงให้ทีมตรวจนับต้นทางก่อน ไม่ลดจำนวนแถวเพื่อสร้างไฟล์ให้สำเร็จ
- ข้อมูลอายุไม่ครบยังอยู่ในไฟล์พร้อมหมายเหตุภาษาไทย อายุที่บันทึกไว้รวม 0 เดือนมีลำดับความสำคัญก่อน หากไม่มีจึงใช้วันเกิดและวันตัดอายุของงาน ไม่ใช้วันที่ดาวน์โหลดและไม่จัดรุ่นใหม่

## ตรวจรับด้วยหน้าจอและ Microsoft Excel หลัง production

ใช้ข้อมูลทดสอบที่ได้รับอนุญาตและมีตัวแทนของกรณีต่อไปนี้ ไม่สร้างใบสมัครหรือแก้กติกางานจริงเพียงเพื่อทำชุดทดสอบ บันทึกวันที่ รุ่นของ Microsoft Excel ระบบปฏิบัติการ commit/deployment ที่ตรวจ และรหัสงาน โดยเก็บภาพหรือไฟล์ที่มีข้อมูลส่วนบุคคลไว้ในพื้นที่ที่ได้รับอนุญาต

1. งานที่ตั้งค่าแล้ว: เปิดหน้าส่งออก ตรวจลำดับชื่อไทย แก้ร่าง ดูตัวอย่าง บันทึก แล้วโหลดใหม่ ยืนยันว่าลำดับคงอยู่ ตรวจคำเตือน ออกจากหน้าร่าง และการบันทึกชนกันตามขั้นตอนด้านบน
2. ดาวน์โหลดจากหน้าส่งออกการแข่งขันและหน้า `/dashboard/event-export` ของงานเดียวกัน ต้องได้ลำดับ คำไทย ยอด และความพร้อมแบบเดียวกัน หน้าเก่ามีทางไปตั้งค่ารูปแบบเดียวกันและข้ามการตรวจไม่ได้
3. เปิด `.xlsx` ด้วย Microsoft Excel ต้องไม่มีข้อความซ่อมไฟล์ ชีตแรกชื่อ “ข้อมูลงาน” แสดง “สารบัญและข้อมูลงาน” พร้อมชื่อเต็ม ระดับ สี เพศ จำนวน และ “เปิดชีต →”
4. คลิกลิงก์สารบัญของชีตแรก กลาง และท้าย ตรวจว่าถึงชีตถูกต้อง แต่ละชีตกด “← กลับสารบัญ” ที่ A1 แล้วกลับมายังแถวของตนในสารบัญได้ ตรวจเพิ่มเติมกับชื่อไทยยาว ชื่อที่มีเครื่องหมายอัญประกาศเดี่ยว และชื่อที่ระบบเติมส่วนท้ายเพื่อไม่ให้ซ้ำ
5. ตรวจว่า A1 เป็นลิงก์กลับ แถวถัดไปยังมีชื่องาน รหัสงาน และชื่อรุ่นครบ หัวตารางและแถวข้อมูลไม่ถูกเขียนทับ ชื่อแท็บสั้นแต่ระบุกลุ่มได้ ส่วนชื่อเต็มและเกณฑ์ที่ทีมใช้ยังอ่านได้ในชีตและสารบัญ
6. ตรวจจำนวนใบสมัครรวมและรหัสใบสมัครให้ครบ ไม่มีซ้ำหรือหาย ไมโครชิพและเบอร์โทรเลขศูนย์นำหน้ายังอยู่ ไมโครชิพเดียวที่สมัครคนละรุ่นหรือคนละระดับต้องคงเป็นหลายใบสมัคร
7. ตรวจ Normal “สมัครสำเร็จ”, Royal “รอตรวจสอบ/อนุมัติแล้ว/ไม่อนุมัติ” และกรณี “ต้องตรวจประเภทงาน” ตามข้อมูลต้นทาง ไฟล์รวมทุกสถานะ ไม่ใช่เฉพาะแถวหรือ filter ที่กำลังเปิด และไม่เปลี่ยนความหมายตามสถานะรายงานตัว
8. เปิด ZIP ใบสมัคร DOCX ตรวจชื่อเต็ม เพศผู้/เมีย สีดำ/เผือก ระดับ สถานะ อายุ 0 เดือน อายุคำนวณจากวันตัดอายุ และอายุไม่ครบให้ตรง Excel โดยรูปแบบใบสมัครเดิมยังใช้งานได้
9. ตรวจงานที่ไม่มีใบสมัครแต่ตั้งค่าพร้อมแล้ว ต้องได้ชีตข้อมูลงานที่ระบุว่าไม่มีข้อมูล ไม่มีลิงก์ลอยไปยังชีตที่ไม่มีอยู่ ตรวจงานที่ยังไม่ตั้งค่าและกรณีคำแปลหรือการผูกกลุ่มขาด ต้องไม่มีไฟล์บางส่วนดาวน์โหลดออกมา
10. ทำซ้ำกับอีกงานที่มีลำดับต่างจากตัวอย่างอุดร แล้วบันทึกผลแยก “ผ่าน/ไม่ผ่าน/ยังไม่ได้ตรวจ” ไม่ใช้ผลอ่าน XML หรือ build แทนผลคลิกจริง

Microsoft Excel เป็นแอปที่ใช้ตรวจรับหลัก ยังไม่อ้างว่าลิงก์ทำงานเหมือนกันใน Google Sheets หรือ Numbers หากต้องใช้แอปอื่น ให้ตรวจและบันทึกแยกต่างหาก

## การปล่อยระบบและการกู้คืน

1. ตรวจ source และ Dashboard PR คู่กัน รวม tests, TypeScript, lint และ build ณ commit ที่จะปล่อย ต้องได้รับอนุญาตจากคุณนนท์ก่อน merge/deploy การมี PR หรือคู่มือนี้ไม่ใช่การอนุญาตปล่อยระบบ
2. ปล่อย source ที่รองรับ `exportPresentationVersion: 1` ก่อน ยืนยัน deployment พร้อม แล้วจึงปล่อย Dashboard ที่ส่ง `x-export-presentation-version: 1` ผ่าน server bridge เดิม ไม่เพิ่ม secret ใน browser และไม่เปลี่ยนฐานข้อมูล/ค่าระบบควายส่วนอื่น
3. ระหว่างรอ Dashboard ใหม่ ผู้ใช้ export รุ่นเก่าจะได้รับข้อความให้อัปเดตอย่างชัดเจน ไม่ควรเปิด generator เก่าที่ให้ไฟล์ผิดเพื่อเลี่ยงข้อความนี้ การแก้ไขงานทั่วไปด้วย client เดิมต้องยังคง metadata รูปแบบไฟล์ไว้
4. งานเก่าต้องมีผู้จัดตรวจลำดับและคำไทยก่อนบันทึกรูปแบบ บันทึกผ่าน API ที่มี revision guard และ audit เท่านั้น เก็บ metadata เดิมก่อนการแก้ที่ได้รับอนุญาต ห้ามเติมลำดับให้ทุกงานด้วยการเดาจากอายุหรือชื่องาน
5. แยกสถานะ “ระบบกลางผ่านการทดสอบ” จาก “ทุกงานเดิมพร้อมส่งออก” การอ้างว่าทุกงานพร้อมต้องอ่าน readiness ครบทุกหน้า รวมงานเก่า งานร่าง งานปิด และทั้ง Normal/Royal จนไม่มีรายการค้าง ณ รอบตรวจล่าสุด รายงานเฉพาะรหัสงาน ความพร้อม จำนวน และรหัสปัญหา ไม่เผยชื่อเจ้าของ เบอร์โทร หรือข้อมูลใบสมัคร
6. หากพบไฟล์ผิด ให้หยุด export ของส่วนที่มีปัญหาและทบทวน commit/config ที่เกี่ยวข้อง ใช้ลำดับคืน Dashboard ก่อน source ที่พึ่งพากัน เก็บ additive metadata, audit, รหัสและใบสมัครเดิม ห้ามลบประวัติหรือคืนทั้งเอกสารงานจาก snapshot เก่า และไม่กลับไปอ้างว่า generator เดิมถูกต้อง
7. สวิตช์ปิดการเขียนข้อมูลของ source ช่วยหยุดการแก้ไข แต่ไม่ใช่สวิตช์ปิด read/export และไม่ย้อนงานที่บันทึกแล้ว กรณีต้องหยุด export ต้องใช้ guard/การ deploy ที่ตรวจทานและได้รับอนุญาตให้ตรงกับปัญหา

ไฟล์ JSON สำหรับทดสอบสัญญาข้อมูลใน `src/test-fixtures/competition-export-contract.json` เป็นข้อมูลสังเคราะห์ที่สร้างและตรวจซ้ำจาก compiler ฝั่ง source แล้วสำเนาเหมือนกันในสอง repository ใช้จับ contract drift ใน CI โดยไม่ต้องเข้าถึงอีก repository หรือ production ไม่ใช่หลักฐานว่ารูปแบบของทุกงานจริงถูกตั้งค่าแล้ว
